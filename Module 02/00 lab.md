# Подробная инструкция: разграничение прав доступа в Azure DevOps Boards с английскими названиями параметров

## Введение

Azure DevOps не имеет встроенной функции «показывать только мои задачи». Права доступа к рабочим элементам контролируются исключительно на уровне **областей (Area Paths)** . Если у пользователя есть право `View work items in this node` для определённой области, он увидит все задачи в этой области, независимо от того, кто их создал или кому они назначены.

Для достижения изоляции пользователей используется проверенный подход: **создание персональной команды и выделенной области для каждого пользователя**, с последующей настройкой прав безопасности на областях.


## 1. Модель безопасности Azure Boards

Безопасность Azure Boards работает на нескольких уровнях:

### 1.1. Access Levels (уровни доступа)

| Access Level | Возможности в Azure Boards |
|---|---|
| **Stakeholder** | Просмотр work items, создание и изменение своих work items, просмотр дашбордов, ограниченный доступ к queries |
| **Basic** | Полный доступ к work items, queries, dashboards, boards и backlogs |
| **Basic + Test Plans** | Включает Basic плюс функции Test Plans |
| **Visual Studio Enterprise** | Включает все функции Basic плюс расширенные возможности |

### 1.2. Security Groups (группы безопасности)

| Группа | Права по умолчанию |
|---|---|
| **Readers** | `View work items in this node` (Area Path permission) |
| **Contributors** | `View work items in this node`, `Edit work items in this node`, `Create tag definition` |
| **Project Administrators** | Все права, включая `View work items in this node`, `Edit work items in this node` |

### 1.3. Object-Level Permissions (права на уровне объектов)

Ключевой уровень для изоляции задач — права на **Area Paths**. Основные permissions:

| Permission | Описание |
|---|---|
| **View work items in this node** | Просмотр work items в узле области. Если установлено `Deny`, пользователь не увидит **ни одного** work item в этой области |
| **Edit work items in this node** | Редактирование work items в узле области |
| **Create child nodes** | Создание дочерних узлов области |
| **Edit this node** | Редактирование самого узла области |
| **View permissions for this node** | Просмотр настроек безопасности узла |

**Критически важно:** `Deny` переопределяет любой `Allow`, даже для членов административных групп.


## 2. Пошаговая инструкция с английскими названиями параметров

### Шаг 1: Создание Area Paths (областей)

1. Перейдите в **Project settings** → **Project configuration** → **Areas**.
2. Создайте корневую область, например: `PersonalWork`.
3. Внутри неё создайте подчинённые области для каждого пользователя:
   - `PersonalWork\User1`
   - `PersonalWork\User2`
   - `PersonalWork\User3`

**Параметры:**
- **Name:** `PersonalWork\User1`
- **Parent Area Path:** `PersonalWork`

### Шаг 2: Создание персональной команды (Team) для каждого пользователя

1. Перейдите в **Project settings** → **Teams** → **New Team**.
2. Создайте команду, например: `User1_Team`.
3. В настройках команды (**Team configuration**) укажите:

**Параметры:**
- **Team name:** `User1_Team`
- **Area Path:** `PersonalWork\User1` (как область по умолчанию)
- **Iteration Path:** оставьте значение по умолчанию или настройте отдельно

4. Добавьте соответствующего пользователя в эту команду.

### Шаг 3: Настройка прав доступа к Area Paths (критический шаг)

1. Вернитесь в **Project settings** → **Project configuration** → **Areas**.
2. Нажмите на три точки (`...`) рядом с областью `PersonalWork\User1`.
3. Выберите **Security**.

**Настройка разрешений для `PersonalWork\User1`:**

| Группа / Пользователь | Permission | Setting |
|---|---|---|
| `User1_Team` (или `User1`) | `View work items in this node` | **Allow** |
| `User1_Team` (или `User1`) | `Edit work items in this node` | **Allow** |
| `Project Valid Users` | `View work items in this node` | **Deny** |
| `Contributors` | `View work items in this node` | **Deny** |
| `Readers` | `View work items in this node` | **Deny** |

4. Повторите эти действия для каждой созданной пользовательской области.

**Рекомендация:** снимите все разрешения с корневой области `PersonalWork`, чтобы права не наследовались автоматически. Это позволит избежать ошибок и упростит администрирование.

### Шаг 4: Распределение пользователей по командам

Каждый пользователь должен быть добавлен **только в свою собственную команду**. Пользователь не должен состоять в командах других пользователей, иначе он получит доступ к их областям.

**Параметры:**
- **Project settings** → **Teams** → `User1_Team` → **Members** → Add `User1`
- Убедитесь, что `User1` не добавлен в `User2_Team`, `User3_Team` и т.д.

### Шаг 5: Назначение правильной области при создании задач

При создании задачи для конкретного пользователя обязательно указывайте в поле **Area** ту область, которая закреплена за этим пользователем.

**Параметры при создании work item:**
- **Title:** Название задачи
- **Assigned To:** `User1` (или оставьте пустым)
- **Area:** `PersonalWork\User1` (обязательно!)
- **Iteration:** любой подходящий спринт

Если задача будет создана в корневой области или в области другого пользователя, она не появится на его доске.

### Шаг 6: Ограничение права создания областей

Чтобы пользователи не могли создавать собственные области в обход настроек, ограничьте право `Create child nodes` для групп, в которых они состоят.

**Параметры:**
- В **Security** для `PersonalWork` установите:
  - `Create child nodes` для `Contributors` → **Deny**
  - `Create child nodes` для `Project Valid Users` → **Deny**

## 4. Важные ограничения и предостережения

### 4.1. Отсутствие совместной работы
Полная изоляция исключает возможность совместной работы над задачами. Пользователи не смогут видеть задачи друг друга, даже если они назначены на них или связаны с ними.

### 4.2. Видимость на доске (Board)
Если задача не помечена нужной областью, пользователь не увидит её на своей доске, даже если она назначена на него.

### 4.3. Права администраторов
Пользователи с правами **Project Administrator** обычно видят все области, и ограничить их не получится.

### 4.4. Теги (Tags)
Теги в Azure DevOps являются общими для всего проекта. Тег, созданный одним пользователем, будет виден всем остальным в списке автодополнения.

### 4.5. Фильтрация vs. Разграничение прав
Фильтр `Assigned to me` на доске — это лишь фильтр отображения. Он не мешает пользователю найти чужие задачи через поиск или запросы, если у него есть доступ к области. Настоящее разграничение прав достигается только через настройку безопасности областей.

### 4.6. Запросы (Queries)
Настройки прав на Area Path также влияют на результаты запросов. Если у пользователя нет права `View work items in this node` для области, он не сможет увидеть соответствующие work items через queries.


## 5. Альтернативный подход: изоляция на уровне команд

Если полная изоляция каждого пользователя не требуется, можно использовать более простой подход — изоляцию на уровне **команд**:

1. Для каждой команды создаётся отдельная область (например, `TeamA`, `TeamB`).
2. Команды настраиваются на использование своих областей.
3. Права на области настраиваются так, чтобы члены одной команды не видели задачи другой команды.

Этот подход проще в администрировании и сохраняет возможность совместной работы внутри команды.


## 6. Итог

Чтобы каждый пользователь видел только свои задачи в Azure DevOps Boards, необходимо:

1. **Создать отдельные Area Paths** для каждого пользователя.
2. **Создать персональные Teams** и привязать их к соответствующим Area Paths.
3. **Настроить Security на Area Paths**, установив `Deny` для `View work items in this node` для всех групп, кроме персональной команды пользователя.
4. **Снять права с корневой области**, чтобы избежать наследования.
5. **Всегда указывать правильную Area** при создании work item.
6. **Ограничить право `Create child nodes`** для обычных пользователей.

Это единственный способ добиться строгой изоляции задач в Azure DevOps. Помните, что полная изоляция исключает совместную работу, поэтому применяйте её только тогда, когда это действительно необходимо. В большинстве случаев достаточно изоляции на уровне команд, которая сохраняет баланс между безопасностью и возможностью сотрудничества.
