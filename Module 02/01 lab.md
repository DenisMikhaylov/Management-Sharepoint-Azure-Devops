# Лабораторная работа: Настройка проектов, команд и прав доступа в Azure DevOps

**Цель работы:** получить практические навыки создания проектов на основе различных процессов (Agile, Scrum, CMMI), создания команд внутри проектов и настройки гранулярных прав доступа к рабочим элементам на основе областей (Area Paths).

**Предварительные требования:**
- Учётная запись Azure DevOps с правами **Project Collection Administrator** (или правами на создание проектов и управление безопасностью на уровне проекта).
- Доступ к веб-порталу `https://dev.azure.com/<Ваша_Организация>`.

---

## Теоретическая справка

Каждый проект в Azure DevOps основан на одном из встроенных процессов, который определяет типы рабочих элементов, их состояния и правила. Основные процессы: **Agile**, **Basic**, **Scrum** и **CMMI**. В одном проекте может быть создано несколько команд. Каждая команда автоматически получает собственную группу безопасности и набор Agile-инструментов (Backlogs, Boards, Sprints).

Области (Area Paths) служат для группировки рабочих элементов по командам, продуктам или функциональным направлениям. **Ключевой механизм безопасности:** права доступа к рабочим элементам можно назначать на уровне Area Path. Если команде запретить доступ к чужой области, её участники не смогут видеть и редактировать рабочие элементы, назначенные на эту область.

**Различия процессов:**
- **Agile** — основан на User Story, поддерживает итеративную разработку с гибким планированием.
- **Scrum** — использует Product Backlog Item (PBI) и Sprint Backlog, включает встроенные Burndown Chart и Sprint Capacity widgets.
- **CMMI** — формализованный процесс с типами Requirement, Change Request, Risk, Review и другими артефактами для управления процессами.

## Часть 1. Проект Lab-Agile (процесс Agile)

### 1.1. Создание проекта

1. Войдите в свою организацию Azure DevOps.
2. Нажмите **New project**.
3. Заполните поля:
   - **Project name:** `Lab-Agile`
   - **Description:** Project for learning Agile process
   - **Visibility:** Private
   - **Version control:** Git
   - **Work item process:** **Agile**
4. Нажмите **Create**.

> **Примечание:** Проект автоматически получает команду по умолчанию с именем `Lab-Agile` и корневую область (Area Path), совпадающую с именем проекта.

### 1.2. Создание команд

1. Откройте проект `Lab-Agile`.
2. Перейдите в **Project settings** → **Teams**.
3. Нажмите **New team**.
4. Введите имя: `Team-Alpha`, добавьте описание по желанию.
5. Нажмите **Create team**.
6. Повторите шаги 3–5 для создания команд `Team-Beta` и `Team-Gamma`.

> **Важно:** После создания каждой команды необходимо назначить ей область по умолчанию (см. п. 1.3), иначе инструменты команды (доски, бэклоги) не будут работать.

### 1.3. Настройка областей (Area Paths)

1. Перейдите в **Project settings** → **Project configuration** → **Areas**.
2. Убедитесь, что корневая область `Lab-Agile` существует.
3. Создайте три дочерние области:
   - Нажмите на корневую область `Lab-Agile`.
   - Нажмите **New child**.
   - Введите имя: `Team-Alpha`, нажмите **Save**.
   - Повторите для `Team-Beta` и `Team-Gamma`.
4. Вернитесь в **Project settings** → **Teams**.
5. Выберите `Team-Alpha`, перейдите на вкладку **Iterations and areas**.
6. В разделе **Areas** нажмите **Add area** и выберите `Lab-Agile\Team-Alpha`. Нажмите **Save and close**.
7. Повторите шаги 5–6 для `Team-Beta` (область `Team-Beta`) и `Team-Gamma` (область `Team-Gamma`).

> **Результат:** Каждая команда «привязана» к своей области. Рабочие элементы, созданные в бэклоге команды, автоматически получают её Area Path.

### 1.4. Настройка прав доступа к рабочим элементам

1. Перейдите в **Project settings** → **Project configuration** → **Areas**.
2. Нажмите на область `Team-Alpha` (или нажмите на три точки справа → **Security**).
3. Откроется окно безопасности для этой области. Вы увидите список групп безопасности, включая группы команд (`Team-Alpha`, `Team-Beta`, `Team-Gamma`).
4. Настройте права для **чужих** команд:
   - Для группы `Team-Beta` установите для разрешения **View work items in this node** значение **Deny**.
   - Для группы `Team-Gamma` сделайте то же самое.
   - Для группы `Team-Alpha` оставьте **Allow** или **Not set**.
5. Повторите шаги 2–4 для области `Team-Beta`: запретите доступ для `Team-Alpha` и `Team-Gamma`.
6. Повторите для области `Team-Gamma`: запретите доступ для `Team-Alpha` и `Team-Beta`.

> **Важно:** Разрешение **Deny** имеет приоритет над **Allow**. Устанавливая Deny на просмотр рабочих элементов в чужой области, вы полностью скрываете эти рабочие элементы от участников команды.

### 1.5. Проверка результата

1. Добавьте тестового пользователя в команду `Team-Alpha` проекта `Lab-Agile`. Для этого: **Project settings** → **Teams** → `Team-Alpha` → **Add** (в разделе Members).
2. Войдите в Azure DevOps под этим пользователем.
3. Создайте рабочий элемент (User Story) в бэклоге команды `Team-Alpha`. Убедитесь, что он отображается.
4. Попробуйте создать рабочий элемент, явно указав Area Path `Lab-Agile\Team-Beta`. Убедитесь, что элемент **не создаётся** или **не отображается** в представлениях команды `Team-Alpha`.
5. Перейдите на доску команды `Team-Beta` (под тем же пользователем). Убедитесь, что рабочие элементы этой команды **не видны**.
